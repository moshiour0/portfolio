Chapter 01

Overview

What the site is, what every file does, and the one architectural rule everything else follows.

A single-page narrative portfolio with five supporting routes. The page tells one story — scrolling down is climbing up — and each section carries a cinematic plate drawn from your own footage.

The visual concept comes straight from the clips: valley floor → river → forest → beneath the water → canopy → strata → ridge → lone tree → survey point → summit. That ordering is not decorative. It is the site's information architecture.

How a render actually happens

  1. Build time. Next prerenders every route. lib/content.ts is read at build, so all copy is in the HTML.
  2. First paint. Aurora gradient, hero poster, all text. No video requested yet.
  3. Hydration. VideoBackdrop checks reduced-motion, Save-Data and device class. Only if all pass does it emit a <source>.
  4. Scroll. One passive listener, sampled inside rAF, decides which section owns the viewport and crossfades the backdrop.

The one architectural rule

Rule

Animation never goes through React. Every moving thing keeps its state in a useRef and writes directly to element.style inside a requestAnimationFrame loop. React mounts things and holds coarse state that changes rarely. A carousel spinning at 60fps triggers zero React renders.

The one exception is deliberate: the dot indicator's setActive is guarded with prev === index ? prev : index, so it fires a few times a minute, not sixty times a second.

This is the single biggest reason the site holds 60fps with a video playing, a WebGL mesh rendering, and five card decks alive at once.

Chapter 02

The video backdrop system

Eleven full-screen clips, one decoder, no stutter — from a desktop to a cheap phone. The most involved part of the build.

Playback lives in the file, not in code

You asked for two behaviours: hero and contact slow gradually to a standstill; everything else plays forward, then runs backwards more slowly and keeps going so the loop is invisible.

The obvious implementation is to drive video.playbackRate from a rAF loop. That was tried first and it was wrong, for two separate reasons:

  • Blink refuses rates below 1/16. Setting playbackRate = 0.0622 throws NotSupportedError. A deceleration easing toward zero walks straight into that floor.
  • It vibrated. Changing the rate every frame means the decoder is asked for frames at times that don't line up with the display refresh. Frames get held for uneven durations, and the eye reads that as shimmer.

So the timing was baked into the video file, and the browser just plays it at rate 1.

Deceleration — a logarithmic time-warp

setpts=(-TAU*log(1-T/S))/TB     TAU = 2.2, S = duration + 0.2s

As T approaches S the logarithm diverges, so timestamps stretch without bound — the clip glides to a halt and rests on its final frame. Set loop = false and it simply stops.

Ping-pong — the reverse leg is inside the file

[0:v]split=2[f][r];
[f]setpts=1.4*PTS[fwd];
[r]reverse,setpts=2.2*PTS[rev];
[fwd][rev]concat=n=2:v=1:a=0

Because the reversed leg ends on frame 0, loop = true gives a seamless there-and-back forever. No seeking, no rAF, no decode stalls, no restart flash.

The vibration fix

Even with timing baked in, the first encodes shimmered. Probing the actual frame presentation times showed durations alternating 0.0417s / 0.0833s — two different frame lengths in one clip. Two causes stacked:

  • setpts=1.8 is not an integer ratio, so resampling produced a mix of held and fresh frames.
  • The sources were 24fps. On a 60Hz display that needs 3:2 pulldown — frames held for 3 refreshes, then 2, then 3. That cadence is visible.
minterpolate=fps=30:mi_mode=mci:mc_mode=aobmc:me_mode=bidir:vsbmc=1

Lesson

If a media behaviour can be expressed in the asset, put it in the asset. Runtime control of playback rate fights the decoder, the compositor and the display refresh all at once.

One decoder, always

Eleven <video> elements exist. At most one ever decodes — every other layer is paused at opacity: 0. That is what makes eleven full-screen clips affordable at all.

A layer only receives <source> children once armed, and arming covers the active clip plus the next one down the page:

The crossfade

Opacity over 1.1s, scale from 1.07 to 1.0 over 2.4s. The mismatch is intentional: the incoming clip is still settling long after it has finished fading in, which reads as a slow push-in rather than a cut. Both are compositor-only properties, so the crossfade costs the main thread nothing.

While a clip is fully opaque, the WebGL mesh underneath is invisible — so a 25-line pub/sub tells it to idle. Note the asymmetry: covering is announced 1200ms late (after the crossfade ends, so the mesh is never missing while still partly visible) but uncovering is announced immediately.

Full-bleed on a phone without losing you

A 16:9 plate on a 390×844 phone, filling the height, shows about 26% of its width. Which 26% is the whole question — in every plate you stand between 10% and 55%, never dead centre. A default centre crop lands on empty landscape.

you should fit height width as well … otherwise video background have not meaning Your rejection of the object-fit: contain attempt

You were right — a letterboxed strip is not a background. The fix keeps cover and moves the crop window: every plate carries a second focal point, centred on the subject box from your asset spec.

focus:       "50% 50%"   // wide screens
focusNarrow: "31% 56%"   // phones — centred on the person
@media (max-width: 900px) {
  .backdrop-video { object-position: var(--focus-narrow); }
}

Verified across all ten plates at 390×844 — every subject box lands inside the visible window, with object-fit still cover.

Choosing sources per device

Gotcha

The media attribute on <source> does not work inside <video>. It is honoured inside <picture>, but browsers dropped it for video. The selection must happen in JavaScript.

H.264 goes first on phones, WebM first on desktop. VP9 is smaller and desktops decode it in hardware — but on phones VP9 hardware decode is inconsistent, and offering it first can silently drop a device into a software decoder.

The orbit path — the interesting maths

The obvious path is an ellipse circumscribing the subject. That was the first implementation and it was wrong. Measurement showed cards still covering 19.5% of the fish.

Why: an ellipse keeps a card's centre point clear. A card is a rectangle. At roughly 45° its corner reaches much further than its centre and cuts into the subject.

const halfW = (geometry.cardWidth * scale) / 2;
const halfH = (geometry.cardHeight * scale) / 2;
const needX = geometry.koW + halfW + 10;
const needY = geometry.koH + halfH + 10;

// distance to the box boundary along this heading =
// the smaller of the two axis crossings
const t = Math.min(
  needX / Math.max(Math.abs(ct), EPS),
  needY / Math.max(Math.abs(st), EPS),
);

Because a box is the intersection of two slabs, that distance is simply the smaller of needX/|cos| and needY/|sin|. The EPS guard prevents division by zero on the axes.

The budget is a floor, not a ceiling

The stage height had been clamped to the budget, so when type grew the cards were sliced. Now:

const cardHeight  = Math.round(tallest || budget * 0.85);
const stageHeight = Math.max(budget, cardHeight + 24);

Where that makes a section overflow a short laptop screen, the padding yields instead. The cards never get cut again. Cards also top out at z-index: 30 against the heading's z-50 — in front of everything except the title, exactly as you specified.

Drag, fling, snap, hold

A five-state machine in a ref, ticked by one rAF loop: auto → drag → fling → snap → hold → auto.

Technique

Easing uses 1 - exp(-k · dt), not × 0.1 per frame. The naive form is frame-rate dependent — it eases twice as fast at 120Hz as at 60Hz. The exponential form gives identical motion on any display.

dt is clamped to 0.05, so a tab backgrounded for ten seconds doesn't teleport the deck on the next frame. Velocity sampling has an 8ms floor, so two events in the same millisecond can't divide by a near-zero dt.

Chapter 04

Layout, type and colour

Why the palette is what it is, and why the font sizes now have arithmetic behind them.

The palette is measured, not chosen

Every clip is the same world — overcast, misty, forest — and the one constant across all eleven is your dim yellow raincoat. That became the identity colour.

TokenValueTaken from
--color-bg#0a0f0eNear-black with a green cast — forest shadow

--color-accent-2#83a0adThe river
--color-accent-3#7a9a55The moss

Because the accent appears in the footage in every section, highlighted text never looks pasted on. And the ground is not neutral grey — when the video fades out, what's underneath still belongs to the same world.

Type that is calculated

You asked why the font sizes had no mathematical basis. They do now. The copy column declares itself a container, so cqw is a share of the measured safe zone, not the window:

column width  W = 56% of a 1152px shell    ≈ 645px on a 1440 frame
display face advance                       ≈ 0.55em per character
longest section title "Capabilities"       = 12 characters

title at 8.4cqw = 0.084 × 645              ≈ 54px
line length     = 12 × 0.55 × 54           ≈ 356px ≈ 55% of column

Comfortably unbroken, with margin to spare. Each size then carries three bounds:

@utility fit-title {
  font-size: clamp(2rem, min(9.2cqw, 6vh), 4rem);
}
  • Floor in rem — never drops below readable.
  • Preferred is min(cqw, vh) — width-derived, capped by height so a short viewport shrinks type instead of pushing the section past one frame.
  • Ceiling in rem — never becomes a billboard on a 4K monitor.

That min(9.2cqw, 6vh) is the whole trick, and it is why "one section, one frame" holds across every screen tested.

Safe-zone columns

Each clip places its subject differently, so the copy column is sized per section — columnPct={32} for skills, 50 for pillars, 56 for exploring — derived from where that clip's subject ends in your asset spec. Below lg the safe zones collapse and copy takes the full width, matching the spec's mobile rule and the scrim, which also goes full-width below 768px.

Detail

Sections use min-h-[100svh], not 100vh. On mobile browsers vh is measured against the viewport with toolbars hidden, so a 100vh section is taller than the visible area until you scroll. svh measures the smallest state.

Chapter 05

Scroll and navigation

Eased scrolling on desktop, native on touch, proximity snap, and a hash landing on a page that grows eightfold while you scroll.

Lenis, on desktop only

if (window.matchMedia("(prefers-reduced-motion: reduce), (pointer: coarse)").matches) {
  return;
}

This is the single most important line in the mobile performance work. Lenis drives scroll position from JavaScript, frame by frame. On a desktop that's a worthwhile trade — a wheel is a coarse input. On a phone it replaces hardware momentum scrolling with main-thread work, and every frame then competes with video decoding.

Proximity snap

Once scrolling stops, the page looks at the nearest section edge. If you've already brought it most of the way in (within 30% of a viewport), it finishes the job. If you're mid-journey between two sections, it leaves you alone.

That distinction is what makes it proximity snap rather than mandatory snapping — it never fights someone deliberately scrolling past.

Nav links that were dead on sub-pages

The nav always called scrollToId(id). That works on the homepage — but from /projects there is no #research element, so the click did nothing at all.

const onHome = usePathname() === "/";

const go = (event, id) => {
  if (!onHome) return;          // let the <Link> navigate to /#id
  event.preventDefault();
  scrollToId(id);
  history.replaceState(null, "", `#${id}`);
};

replaceState rather than pushState — so the back button returns to the previous page, not through every section you scrolled past.

The hard half: landing on the right place

Homepage height
1,900 → 14,851px
as sections lay out and carousels measure

Scrolling immediately aims at a position that no longer exists a moment later. So HashScroll waits for the document height to stop changing:

// height unchanged for a few consecutive frames = layout has landed
stableFor = height === lastHeight ? stableFor + 1 : 0;
if (!el || (stableFor < 6 && waited < 120)) {
  raf = requestAnimationFrame(settleThenScroll);
  return;
}
scrollToId(id);

Then it re-confirms the landing at 1300, 2200, 3200 and 4400ms, because the carousels keep adding height afterwards and how long depends on which route you came from. Once within 6px the checks are no-ops.

Technique

Every scroll listener here schedules a rAF and cancels the previous one, so a burst of scroll events produces exactly one computation per frame, not twenty. Reading getBoundingClientRect() directly in a scroll handler forces synchronous layout mid-scroll.

An honest limitation

What the instrument could not see

After the mobile encodes landed, the harness median stayed around 200–280 ms. That is not a measure of a real phone.

Headless Chromium runs on SwiftShader — a software rasteriser with no hardware video decode. Every frame is decoded on the CPU and composited in software, then throttled a further 4×. On a real phone, decode happens in dedicated silicon and compositing on the GPU.

So the harness cannot show the video improvement, and no amount of tuning would have driven its number to 17 ms without removing video entirely. What it can measure honestly is structure — and those counts are device-independent. Know which of your measurements describe your code and which describe your measuring instrument.

Desktop is deliberately untouched

Verified live at 1440×900: lenis true, webgl true, backdropFilters 52, WebM sources, zero errors, no mobile encodes leaking through. Every mobile optimisation is gated behind (pointer: coarse) or a width query.

Chapter 07

The content model

Your 36-page brief became 956 lines of typed data — the single source of truth for every word on the site.

No CMS, no markdown files, no JSON blobs. One TypeScript module, because a missing field becomes a build error rather than a rendered gap; because everything is prerendered so all copy sits in the HTML; and because renaming a field shows you every component that used it.

Rules encoded from your brief

/** Verified links only, as the spec requires. */
export const links: SocialLink[] = [ ... ];

/** Honest label: Project / Research Exploration /
    Architecture Study / Competition Project. */
label: string;

/** At most five, per the card design rule. */
tags: string[];

The label field matters. Your brief was insistent that work be described accurately — a research exploration should not be presented as a shipped project. That distinction lives in the data, so every surface that renders a project renders the honest label with it.

No invented metrics. Nothing in the file states a statistic that was not in your brief. Where a project has no measured outcome, none is claimed.

One project, two surfaces

Project carries a short form and a detail object. The carousel card reads the top-level fields; app/projects/[slug]/page.tsx reads detail and generates a page per project at build time. Add a project to the array and its page exists — no routing to write.

What was removed

The Allama Iqbal scholarship content was removed at your request, in full, before anything was committed or published. Verified absent from source, from the build output, and from the deployed site.

Worth knowing

When checking something is genuinely gone rather than hidden, grep the build output as well as the source — content can survive in a stale .next/ long after it leaves the code.

Chapter 08

Failures and fixes

Every significant thing that went wrong, what caused it, and how it was found. Including my own mistakes — those are the most useful ones.

A · SEVERE

Your assets were deleted

What

While replacing the previous identity's content, I deleted the public/ folder believing it belonged to the old site. It contained your videos, portrait and spec files.

Caught by

You. "DID YOU remove previous public folder all content?? it was my content of moshiours"

Recovery

Videos from a scratchpad backup made earlier in the session; portrait and specs from your Downloads; posters regenerated from originals.

Changed

A gitignored .assets-originals/ now holds untouched sources, so every derived asset can be rebuilt without anything outside the project.

Lesson — the most important one here

Never delete a directory containing user-supplied material as part of a refactor. Content that looks like it belongs to something being replaced may be the only copy of something irreplaceable. Back up first, delete second, and prefer moving to deleting.

B1

NotSupportedError on playbackRate

Cause

My guard stopped at <= 0.06. Blink's actual floor is 1/16 = 0.0625. The window between them was exactly where it threw.

Real fix

The whole rate-driving approach was replaced by baking timing into the file. The constant no longer exists, because nothing sets a rate other than 1.

B2

My own test failed to catch B1

Cause

The verification sampled every 1200ms. The failing rate window lasted less than that, so the test stepped straight over the bug and reported success. Fixed by sampling every 120ms.

Lesson

A test that samples more slowly than the phenomenon it watches will report whatever it likes. When testing a transient, your sampling rate is part of the test's correctness.

C2

The orbit fallback left stale geometry

Symptom

On a 390px phone the section produced 535px of content — horizontal overflow.

Cause

When there wasn't width to orbit, the code set the layout to ring and then returned — before measuring ring geometry, leaving placeholder values in place.

Fix

Fall through to the ring branch so geometry is actually computed.

Lesson

An early return in a measurement function is a trap: you change a mode without producing the values that mode needs.

C3

Infinite re-measurement

Cause

keepOut is passed as an inline object literal — a new identity every render. With it in the dependency array, the effect re-ran every render, which re-measured, which re-rendered.

Fix

Destructure to primitives at the top of the component and depend on those.

Lesson

Never put an object or array prop in a dependency array unless the caller memoises it.

C4

Geometry that depended on scroll position

Symptom

Content rendered at y = −2415 — far off screen.

Cause

The keep-out is a share of the viewport, but I computed the host offset from getBoundingClientRect(), which moves as you scroll.

Fix

Measure relative to the section. Each section is exactly one frame tall, so section and viewport coordinates coincide whenever it's on screen — and the result stops depending on where the page happens to be.

C6

The negative margin dragged the deck into the heading

Cause

The padding/negative-margin trick was applied to the same element that carried the height, so the margin pulled that sized box upward.

Fix

Split into two elements: .carousel-viewport is the clip box with the ±120px air, .carousel-stage is the sized element.

Chapter 09

Extending the site

Recipes for the changes you are most likely to want.

Add a background clip

Produce the asset with the ping-pong graph, then make the phone encode too — that is what keeps mobile smooth:

ffmpeg -i public/video/12-new.mp4 -an -vf scale=854:480:flags=lanczos \
  -c:v libx264 -crf 27 -preset slow -profile:v main -level 3.1 \
  -pix_fmt yuv420p -movflags +faststart public/video/m/12-new.mp4

Then register it in lib/backdrops.ts:

{
  id: "new-thing",              // must match the section id exactly
  playback: "pingpong",
  webm:      "/video/12-new.webm",
  mp4:       "/video/12-new.mp4",
  mp4Mobile: "/video/m/12-new.mp4",
  poster:    "/poster/12-new.jpg",
  focus:       "50% 50%",
  focusNarrow: "32% 48%",          // midpoint of the subject box
  scrim: "right",                 // "left" or "even" as needed
  alt: "Description, used for the reduced-motion still",
}

Everything else — lazy loading, one-decode-at-a-time, crossfading, reduced-motion fallback, scroll pausing — picks it up automatically.

Add a section

Four files, in order: content in lib/content.ts; a component in components/sections/; the id added to SECTION_ORDER in lib/backdrops.ts (this is what binds it to the backdrop engine and the snap); and composed into app/page.tsx.

Change the palette

Change --color-accent in @theme and every accent follows — headings, dots, focus rings, the text gradient, the card glow. If you change --color-bg, also update the scrim gradients, which hard-code rgba(10, 15, 14, …) to match.

Adjust a carousel

<Carousel3D
  variant="coverflow"    // "coverflow" | "orbit" | "ring"
  speed={7}              // degrees per second while idling
  budgetVh={52}          // share of viewport height the deck may use
  holdMs={2600}          // pause after a snap, so a card can be read
/>

If a section starts overflowing after you add content, lower budgetVh before touching anything else.

Before you ship

npx tsc --noEmit · npm run build · then the harness in chapter 10 against the production build. A dev build carries HMR machinery and unminified React — its performance numbers are meaningless.

Chapter 10

How everything was verified

The measurement harness — thirteen scripts, now in tools/verify/.

Almost every hard problem here was solved the same way: write something that can see the problem as a number, then change code until the number is right. "The cards overlap the fish" is an argument. "19.5% of the subject box is covered" is a fact you can fix and re-check.

Techniques worth reusing

Emulate a phone properly

const ctx = await browser.newContext({
  viewport: { width: 390, height: 844 },
  deviceScaleFactor: 2,
  isMobile: true,
  hasTouch: true,   // ← without this, (pointer: coarse) is false
});

hasTouch is the one people forget. Without it, every (pointer: coarse) query evaluates false and you are silently testing the desktop path while believing you are testing mobile.

Measure frame times, not vibes

Report the median, p95 and worst — an average hides exactly the stutters you're chasing. Count "janky" frames (over ~32ms) as a share of total, and catch long tasks with a PerformanceObserver; longTaskMax is often more diagnostic than the median because it points at one specific bad operation.

Census the page structure

backdropFilters: [...document.querySelectorAll("*")]
  .filter(e => getComputedStyle(e).backdropFilter !== "none").length

These counts are device-independent — unlike frame times, they mean the same thing on any machine. When your instrument is unreliable, structural counts are what you can still trust.

Always establish a floor

"200ms is bad" is not actionable until you know what the page could reach. Running the same build with video disabled gave 17ms, which proved the entire remaining cost was decode — and therefore that no amount of DOM tuning would help.

Prove the negative

One script asserts that a reduced-motion visitor downloads nothing. Testing that something does not happen is often more valuable than testing that it does.

Measure geometry, not screenshots

const overlap = Math.max(0, Math.min(a.right, b.right) - Math.max(a.left, b.left))
              * Math.max(0, Math.min(a.bottom, b.bottom) - Math.max(a.top, b.top));
const pct = (overlap / (b.width * b.height)) * 100;

This is what turned "the cards are on the fish" into 78% → 19.5% → 0.6%. Screenshots tell you something is wrong; geometry tells you how wrong, and whether your fix helped.
